# 文件结构设计、表格字段与系统实现

## 1. 设计原则

本系统采用“本地项目目录 + JSON 数据文件 + Markdown/ PDF 产物文件”的组织方式。`.xlsx` 只作为导出和交换格式，不作为 Web 系统的唯一真实数据源。

核心原则：

- 每个研究主题对应一个独立本地项目目录。
- 项目内部真实数据优先使用 `JSON`。
- AI 生成的可读内容使用 `Markdown` 保存。
- PDF、BibTeX、导出表格以文件形式保存。
- 项目内表不重复保存 `project_id`，项目目录本身就是数据边界。
- 页面展示数据必须来自项目目录中的真实文件。

项目目录命名格式：

```text
YYYYMMDD-HHMMSS-用户给的项目名
```

示例：

```text
20260529-153000-本地文献综述工作台
```

项目名需要做文件夹安全处理：去除非法字符、空格转连接符、允许保留中文。

## 3. 核心数据文件

### 3.1 project.json

`project.json` 保存项目基本信息。

| 字段名 | 说明 |
| --- | --- |
| `project_name` | 用户输入的项目名称 |
| `project_slug` | 安全化后的项目目录名片段 |
| `description` | 研究说明 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `active_task` | 当前主要任务，可为空 |

### 3.2 candidate_papers.json

`candidate_papers.json` 保存文献检索得到的候选文献。多次检索写入同一个候选池，写入前执行去重。

| 字段名 | 说明 |
| --- | --- |
| `candidate_id` | 候选文献本地唯一 ID |
| `title` | 标题 |
| `authors` | 作者列表 |
| `year` | 年份 |
| `venue` | 发表 venue |
| `paper_url` | 论文详情页或原始链接 |
| `doi` | DOI |
| `abstract` | 英文原摘要，快速检索允许为空 |
| `abstract_zh` | 中文摘要，用于候选卡片展示 |
| `keywords` | 关键词，最多保留前 4 个 |
| `pdf_url` | 开放 PDF 链接，允许为空 |
| `source_mode` | 候选来源模式：`quick` 或 `deep` |
| `import_status` | 是否已导入知识库 |

不放入候选池主表的字段：

| 字段名 | 原因 |
| --- | --- |
| `platforms` | 属于检索过程信息，必要时放入 `search_runs/*.json` |
| `expanded_queries` | 属于检索任务上下文，必要时放入 `search_runs/*.json` |
| `citation_count` | 当前候选卡片不依赖，暂不进入主表 |
| `open_access_status` | 当前候选卡片不依赖，暂不进入主表 |
| `full_text_status` | 当前候选卡片不依赖，PDF 展示优先使用 `pdf_url` |

去重优先级：

1. `doi` 相同视为同一篇。
2. `paper_url` 相同视为同一篇。
3. 都缺失时，对标准化后的 `title + year` 做比较。

字段枚举：

```text
import_status = 未导入 / 已导入
```

```text
source_mode = quick / deep
```

### 3.3 search_runs/*.json

`search_runs/*.json` 记录每次检索任务的原始结构化结果。无论快速检索还是深度检索，都只先写入 `search_runs/<run_id>.json`；随后由后端 normalizer 统一合并生成或更新 `candidate_papers.json`。

| 字段名 | 说明 |
| --- | --- |
| `run_id` | 本次检索任务 ID |
| `user_request` | 用户在网页检索框输入的完整检索要求，不再视为单一主题词 |
| `search_mode` | `quick` 或 `deep` |
| `status` | success / failed |
| `results` | 本次检索得到的论文数组 |

快速检索结果结构：

```json
{
  "run_id": "run-20260601-xxxxxx",
  "user_request": "帮我找 2022 年以来多模态大模型在机器人双臂操作上的代表论文，先给 3 篇最相关的",
  "search_mode": "quick",
  "status": "success",
  "results": [
    {
      "title": "论文标题必填",
      "authors": ["作者1", "作者2"],
      "year": 2024,
      "venue": "会议或期刊",
      "paper_url": "https://...",
      "doi": "10....",
      "abstract_zh": "一两句中文摘要",
      "pdf_url": "https://..."
    }
  ]
}
```

深度检索结果结构：

```json
{
  "run_id": "run-20260601-xxxxxx",
  "user_request": "帮我找 2022 年以来多模态大模型在机器人双臂操作上的代表论文，先给 3 篇最相关的",
  "search_mode": "deep",
  "status": "success",
  "results": [
    {
      "title": "论文标题必填",
      "authors": ["作者1", "作者2", "作者3"],
      "year": 2024,
      "venue": "会议或期刊",
      "paper_url": "https://...",
      "doi": "10....",
      "abstract": "英文原摘要",
      "keywords": ["关键词1", "关键词2", "关键词3", "关键词4"],
      "abstract_zh": "根据英文摘要翻译并简化后的中文摘要",
      "pdf_url": "https://..."
    }
  ]
}
```

检索结果采用“Codex 生成单次结果包 + 后端确定性归一化”的方式：

1. Web 表单提交的是 `user_request`，即完整检索要求，而不是单一 `topic`。
2. 快速检索不显式使用学术检索 skill，目标是快速返回代表论文。
3. 深度检索通过 `SkillInput(name="academic-search-only", path=str((BASE_DIR / "skills" / "academic-search-only" / "SKILL.md").resolve()))` 显式注入仓库内置 skill。这里必须使用仓库根目录构造出的绝对路径，不依赖 Codex runtime 的 `cwd` 相对解析。
4. 两种模式都只写入 `search_runs/<run_id>.json`，不直接修改 `candidate_papers.json`。
5. 后端 normalizer 读取 `search_runs/<run_id>.json` 的 `results`，统一去重并合并到 `candidate_papers.json`。
6. Codex 的最终回复由 Web 对话框展示，只保留“推荐优先阅读哪篇、原因、共找到多少篇”等面向用户的信息，不暴露本地路径、脚本路径和内部执行细节。

后端归一化映射：

| candidate 字段 | raw 来源 |
| --- | --- |
| `title` | `raw.title` |
| `authors` | `raw.authors` |
| `year` | `raw.year` |
| `venue` | `raw.venue` |
| `paper_url` | `raw.paper_url` |
| `doi` | `raw.doi` |
| `abstract` | `raw.abstract` |
| `abstract_zh` | `raw.abstract_zh` |
| `keywords` | `raw.keywords` |
| `pdf_url` | `raw.pdf_url` |
| `source_mode` | `search_runs.search_mode` |
| `import_status` | 后端固定初始化为 `未导入` |

### 3.4 library_papers.json

`library_papers.json` 保存正式纳入项目知识库的文献，是知识库页、论文研读页、综述写作页的主要数据来源。

| 字段名 | 说明 |
| --- | --- |
| `paper_id` | 知识库主键 |
| `candidate_id` | 来源候选文献 ID，可为空 |
| `title` | 标题 |
| `authors` | 作者列表 |
| `year` | 年份 |
| `venue` | 发表 venue |
| `paper_url` | 论文链接 |
| `doi` | DOI |
| `abstract` | 英文原摘要，允许为空 |
| `abstract_zh` | 中文摘要 |
| `keywords` | 关键词 |
| `tags` | 用户标签，例如 `重点 / 方法类 / 综述 / 自定义标签` |
| `notes` | 用户手写简短备注 |
| `pdf_url` | 当前已知开放 PDF 链接，允许为空 |
| `pdf_status` | 本地 PDF 处理状态 |
| `pdf_path` | 项目内 PDF 固定保存路径，导入知识库时即写入，例如 `papers/<paper_id>/paper.pdf` |
| `bibtex_status` | BibTeX 处理状态 |
| `bibtex_path` | BibTeX 文件路径 |
| `has_structured_reading` | 是否已经生成文献矩阵结构化 JSON，导入知识库时固定为 `false` |
| `structured_reading_json_path` | 文献矩阵结构化 JSON 的本地路径 |
| `imported_at` | 导入时间 |
| `updated_at` | 更新时间 |

字段枚举：

```text
pdf_status = 可下载 / 已下载 / 手动导入 / 无来源 / 下载失败
```

```text
bibtex_status = 未生成 / 已生成 / 手动导入 / 生成失败 / 无来源
```

当前阶段不在 `library_papers.json` 中保存 `id`、`source`、`status`、`read_status`、`source_mode`、`notes_summary` 和内嵌 `reading` 对象：

- `paper_id` 是知识库主键，替代旧版重复字段 `id`。
- `venue` 替代旧版重复字段 `source`。
- `source_mode` 只保留在 `candidate_papers.json` 中，用于说明候选来自快速检索还是深度检索。
- 文献矩阵结果由 `has_structured_reading` 和 `structured_reading_json_path` 表达，真正的矩阵内容后续写入 `papers/<paper_id>/reading.json`。
- 导入知识库时不创建有效的 `reading.json`，避免把“已导入”误判为“已研读”。

### 3.5 project_tags.json

`project_tags.json` 保存用户在当前项目中新增的自定义标签。内置标签 `重点 / 方法类 / 综述` 不写入该文件，由系统固定提供。用户在知识库页新增自定义标签后，标签会进入项目级标签库，后续文献可以直接勾选复用；删除自定义标签时，会从标签库和所有已标注文献中同步移除。

文件结构：

```json
["不重要", "实验类", "数据集"]
```

### 3.6 library_chat.json / library_chat_state.json / library_chat_tasks.json

知识库问答是知识库页的多轮对话能力。用户先在表格中勾选文献，再在页面底部对话框提问。后端会把勾选文献的标题、作者、年份、venue、DOI、论文链接、PDF 本地路径、标签、备注和摘要组织进提示词，并通过同一个 Codex thread 持续对话。

`library_chat.json` 保存页面可展示的消息：

| 字段名 | 说明 |
| --- | --- |
| `role` | `user` 或 `assistant` |
| `content` | 消息正文 |
| `created_at` | 创建时间 |
| `run_id` | 本轮问答任务 ID |
| `thread_id` | assistant 消息对应的 Codex thread ID |
| `selected_paper_ids` | 本轮勾选的知识库文献 ID |

`library_chat_state.json` 保存当前项目复用的 Codex thread：

| 字段名 | 说明 |
| --- | --- |
| `thread_id` | 当前知识库问答线程 ID |
| `created_at` | 首次创建时间 |
| `updated_at` | 最近一次成功问答时间 |
| `last_context_paper_ids` | 最近一次已经注入到线程中的勾选文献 ID 集合 |

`library_chat_tasks.json` 保存后台任务进度，用于页面轮询刷新：

| 字段名 | 说明 |
| --- | --- |
| `run_id` | 本轮问答任务 ID |
| `status` | `running / success / failed` |
| `user_question` | 用户问题 |
| `selected_paper_ids` | 本轮勾选文献 |
| `events` | 后台进度事件 |
| `started_at` | 开始时间 |
| `finished_at` | 结束时间 |

实现约束：

- 知识库问答不在每次提问时新建独立智能体；同一项目默认复用 `library_chat_state.json` 中的 `thread_id`。
- 本轮回答必须优先基于当前勾选文献；历史记忆用于延续对话，但不能替代本轮选择范围。
- 如果是新线程第一次问答，或本轮勾选文献相对 `last_context_paper_ids` 有增加/减少，则重新把勾选文献上下文注入 Codex。
- 如果本轮勾选文献没有变化，则不重复注入完整论文上下文，只发送用户问题并要求 Codex 沿用当前线程记忆。
- 用户点击“重置对话”时，系统清空 `library_chat_state.json`，下一次提问会创建新的 Codex thread；`library_chat.json` 中追加“新的对话”分割线，以便保留历史记录但清晰区分新旧上下文。
- 如果本地 PDF 存在，Codex 可在项目目录范围内读取 PDF 辅助回答；如果不存在，则基于元数据、摘要、备注和链接回答。
- Web 表单、JSON 文件和 Codex SDK 调用链路统一使用 UTF-8；PowerShell 手工测试时的编码问题不进入正式系统链路。

### 3.7 reading_matrix_fields.json / reading_matrix_tasks.json / reading.json

文献矩阵用于把已导入知识库且已有本地 PDF 的论文转化为统一字段结构。字段配置在知识库页维护，论文研读页只读展示。

`reading_matrix_fields.json` 保存项目级字段配置，默认字段为 `研究问题 / 方法思路 / 实验设置 / 核心结论`：

| 字段名 | 说明 |
| --- | --- |
| `field_id` | 字段稳定 ID，用于关联 `reading.json` |
| `name` | 字段显示名称 |
| `rule` | AI 判断依据和格式要求 |
| `rule_hash` | 基于 `rule` 生成的 hash，用于判断已有结果是否需要重跑 |
| `order` | 展示顺序 |
| `enabled` | 是否启用 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

`reading_matrix_tasks.json` 保存批量生成任务状态：

| 字段名 | 说明 |
| --- | --- |
| `run_id` | 本次文献矩阵任务 ID |
| `status` | `running / success / failed / stopped` |
| `selected_paper_ids` | 本次勾选论文 |
| `mode` | `skip_existing / overwrite_existing` |
| `total` | 本次实际可处理论文数 |
| `completed` | 已完成数量 |
| `failed` | 失败数量 |
| `current_paper_id` | 当前正在处理的论文 |
| `events` | 任务进度事件 |
| `started_at` | 开始时间 |
| `finished_at` | 结束时间 |

每篇论文的矩阵结果写入：

```text
papers/<paper_id>/reading.json
```

`reading.json` 结构：

```json
{
  "paper_id": "paper-xxx",
  "generated_at": "2026-06-01T17:30:00",
  "field_version": "auto",
  "fields": {
    "research_question": {
      "name": "研究问题",
      "rule": "判断论文要解决的核心科学问题或工程问题；输出 1-2 句中文。",
      "rule_hash": "...",
      "value": "..."
    }
  }
}
```

实现约束：

- 知识库页负责字段编辑和批量运行；论文研读页只负责展示。
- 运行文献矩阵前必须勾选论文，且论文必须已有本地 PDF。
- 批量任务逐篇处理，每完成一篇立即写入 `reading.json`，并把 `library_papers.json` 中的 `has_structured_reading` 更新为 `true`。
- 字段变化后自动迁移已有 `reading.json`：新增字段补空值，删除字段移除，修改名称同步；修改“判断依据和格式要求”会清空该字段已有值，并等待下次增量生成。
- 运行策略由用户选择：`skip_existing` 只处理缺失、空白或 `rule_hash` 过期的字段；`overwrite_existing` 处理当前启用的全部字段。
- 单篇生成时只把本轮待补字段交给 Codex，返回结果与已有 `reading.json` 合并，不重写无关字段。

### 3.8 reading_notes.json

`reading_notes.json` 作为后续 AI 研读笔记的扩展索引。当前 MVP 阶段不在导入知识库时写入默认笔记，也不强制生成 Markdown 笔记；优先通过 `library_papers.json` 的 `has_structured_reading` 和 `structured_reading_json_path` 管理“文献矩阵”状态。

| 字段名 | 说明 |
| --- | --- |
| `note_id` | 笔记唯一 ID |
| `paper_id` | 关联论文 |
| `note_title` | 笔记标题 |
| `note_type` | ai / manual / custom_parse |
| `is_primary` | 是否为主笔记 |
| `markdown_path` | Markdown 笔记路径 |
| `structured_json_path` | 结构化 JSON 路径 |
| `summary` | 列表展示摘要 |
| `parser_name` | 自定义解析名称，可为空 |
| `parser_rule` | 自定义解析判断规则，可为空 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### 3.9 综述写作文件

综述写作页采用四阶段工作台：`拟定主题 -> 大纲生成 -> 内容核对 -> 综述生成`。四个阶段共享同一个本地 CSV、同一个 Codex thread 和同一份对话记录。

`writing_state.json` 保存写作工作台状态：

| 字段名 | 说明 |
| --- | --- |
| `current_stage` | 当前阶段：`topic / outline / mapping / draft` |
| `selected_paper_ids` | 当前纳入综述写作 CSV 的论文 |
| `active_matrix_paper_id` | 阶段一左下文献矩阵预览当前论文 |
| `topic` | 用户通过写作对话选定的综述主题，允许为空 |
| `csv_hash` | `writing_sources.csv` 当前内容 hash |
| `outline_hash` | `outline.md` 当前内容 hash |
| `draft_hash` | `survey.md` 当前内容 hash |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

`writing_chat.json` 保存综述写作对话消息。AI 消息可带 `actions` 字段，用于渲染“跳转检索”“跳转文献矩阵”和题目选择按钮：

```json
{
  "topic_options": [{"id": "A", "title": "候选主题", "reason": "选择理由"}],
  "search_prompts": [{"label": "补充检索", "request": "完整检索要求"}],
  "matrix_field_suggestions": [{"name": "任务类型", "rule": "判断依据和格式要求"}]
}
```

`writing_chat_state.json` 保存 Codex thread，例如 `thread_id`、上一轮阶段和各文件 hash；`writing_chat_tasks.json` 保存后台运行状态和流式过程事件，用于页面轮询、停止和恢复显示。

`outputs/writing/writing_sources.csv` 是综述写作基础 CSV。进入写作页时自动生成/刷新，默认纳入 `has_structured_reading=true` 的论文；阶段一勾选变化后立即更新。CSV 字段为：

```text
paper_id,title,authors,year,venue,abstract_zh,matrix_<文献矩阵字段名>,paper_dir
```

其中 `matrix_<文献矩阵字段名>` 按 `reading_matrix_fields.json` 动态展开；`paper_dir` 指向 `papers/<paper_id>`，目录中可包含 PDF 和相关资料。第三阶段不再把写作分配写回 CSV。

`outputs/writing/writing_section_mappings.json` 是第三阶段“内容核对”的正式数据源。每条记录表示“某个小节中使用某篇论文”，用于第四阶段生成正文：

```json
{
  "mapping_id": "section-3-3__paper-xxx",
  "section_id": "section-3-3",
  "section_title": "3.3 RDT-1B 与 H-RDT：扩散式基础模型与人类操作先验",
  "section_order": 8,
  "paper_id": "paper-xxx",
  "paper_title": "论文标题",
  "citation_role": "核心证据",
  "writing_note": "本小节中这篇文献具体写什么。",
  "evidence_detail": "可写入正文的真实方法、实验、数据或论据细节。",
  "missing_detail": "仍需从 PDF 或资料补查的内容。",
  "source_basis": ["writing_sources.csv", "文献矩阵", "paper_dir"],
  "updated_at": "..."
}
```

第三阶段运行时按 `outline.md` 的叶子小节处理：如果 `1` 下面已有 `1.1 / 1.2`，则 `1` 只作为父级章节，不进入分配和页面卡片；只有没有下级子节的章节才作为写作分配单元。每完成一个叶子小节就覆盖该小节旧映射并写入 `writing_section_mappings.json`；页面默认只显示已分配到该小节的文献卡片，并允许用户修改或删除。

`outputs/writing/outline.md` 是用户可编辑的大纲文件。第二阶段发送对话前，如果检测到大纲 hash 变化，本轮提示词会显式说明以最新 `outline.md` 为准。

`outputs/writing/survey.md` 是最终综述 Markdown。第四阶段要求 Codex 直接编辑该文件，右侧聊天只说明完成内容和需要确认的事项，不把完整正文塞进聊天气泡。第一版正文引用使用数字引用 `[1]`，并在 Markdown 末尾生成“参考文献”列表。

跳转规则：

- `跳转检索` 只把完整检索要求预填到文献检索页，不自动运行。
- `跳转文献矩阵` 只把 AI 建议字段作为未保存草稿追加到知识库页文献矩阵区域，不自动保存。
- 用户点击题目选项后写入 `writing_state.json.topic`，后续写作提示词自动带入该主题。

## 5. academic-search-only 接入设计

`academic-search-only` 作为系统深度检索的结构化学术检索能力层，负责产出 JSON-ready 候选论文记录。PDF 下载不放在 skill 内完成，而由 Web 后端根据 `pdf_url` 统一处理。

本项目内置一份 skill 副本：

```text
skills/academic-search-only/
```

后端调用 Codex SDK 时，应通过仓库根目录构造绝对路径并显式传入 skill，而不是依赖全局用户目录中的 skill，也不依赖运行时 `cwd` 解析相对路径：

```python
SkillInput(
    name="academic-search-only",
    path=str((BASE_DIR / "skills" / "academic-search-only" / "SKILL.md").resolve()),
)
```

可接入能力：

- 多源检索：arXiv、Semantic Scholar、OpenAlex、Crossref、PubMed 等。
- 元数据补全：DOI、venue、作者、引用数、开放获取状态。
- 全文状态判定：`open_pdf / needs_institution / no_open_pdf / anti_bot_blocked / html_not_pdf / unknown`。
- 开放 PDF 链接识别：只填写合法开放 PDF 或开放全文 PDF 的 `pdf_url`。
- 不负责批量下载 PDF；后端的“下载 PDF”按钮使用 `library_papers.json` 中的 `pdf_url` 完成下载。
- 不暴露本地路径、脚本路径、内部工具选择和实现过程。

### 5.1 PDF 批量下载流程

知识库页按钮命名为“下载 PDF”。当前 MVP 阶段直接使用 `library_papers.json` 中已有的 `pdf_url` 下载开放 PDF，不生成 manifest。

流程：

1. 从 `library_papers.json` 中筛选用户勾选且 `pdf_url` 非空的论文。
2. 对每篇文献读取 `pdf_path`，目标位置固定为 `papers/<paper_id>/paper.pdf`。
3. 后端校验 `pdf_url` 为 `http/https`，并检查返回内容是 PDF。
4. 下载成功后写入 `papers/<paper_id>/paper.pdf`，并回写 `library_papers.json` 的 `pdf_status = 已下载`。
5. 下载失败则回写 `pdf_status = 下载失败`，无 `pdf_url` 则保持或回写 `pdf_status = 无来源`。

### 5.2 手动上传 PDF 流程

当开放 PDF 无法自动下载时，用户可以在知识库页单篇上传 PDF。系统将上传文件统一重命名并保存到 `pdf_path` 指定的位置：

```text
papers/<paper_id>/paper.pdf
```

上传成功后，系统回写：

```text
pdf_status = 手动导入
```

字段映射：

| academic-search-only 字段 | 系统字段 |
| --- | --- |
| `pdf_url` | `pdf_url` |
| `download_status = eligible` | `pdf_status = 可下载` |
| `download_status = downloaded` | `pdf_status = 已下载` |
| `download_status = skipped` | `pdf_status = 无法获取` |
| `download_status = failed` | `pdf_status = 下载失败` |
| `local_pdf_path` | `pdf_path` |

实现边界：

- 只下载 `pdf_url` 非空且指向合法开放 PDF 的文献。
- 不调用 Sci-Hub、LibGen、WebVPN、Tor 或其他绕过付费墙的工具。
- 对限流、超时、无开放 PDF 等情况记录状态和原因，不视为系统异常。

### 5.3 BibTeX 补全并导出流程

知识库页按钮命名为“BibTeX 补全并导出”。点击后启动后台任务并显示数量进度条：

1. 遍历当前项目 `library_papers.json` 中所有 `bibtex_status != 已生成` 且 `bibtex_status != 手动导入` 的文献。
2. 对每篇文献按 `doi -> arxiv_id -> paper_url -> title` 的优先级构造输入，调用 `doi2bib3.fetch_bibtex(...)`。
3. 单篇生成成功后写入 `papers/<paper_id>/bibtex.bib`，并回写 `bibtex_status = 已生成`、`bibtex_path = papers/<paper_id>/bibtex.bib`。
4. 没有可用输入时回写 `bibtex_status = 无来源`；调用失败时回写 `bibtex_status = 生成失败`。
5. 所有补全步骤结束后，只合并用户本次勾选且已生成 BibTeX 的文献，写入 `exports/references-<run_id>.bib` 并返回浏览器下载。
6. 合并导出时检测重复 citation key，重复 key 自动追加 `_2`、`_3` 等后缀。

`bibtex_tasks.json` 记录本次后台任务状态：

| 字段名 | 说明 |
| --- | --- |
| `run_id` | 本次 BibTeX 任务 ID |
| `status` | `running / success / failed / stopped` |
| `selected_paper_ids` | 本次要导出的勾选文献 |
| `total` | 本次需要补全的文献数 |
| `completed` | 已生成数量 |
| `failed` | 生成失败数量 |
| `skipped` | 无来源跳过数量 |
| `export_path` | 合并导出的 `.bib` 文件路径 |
| `events` | 任务进度事件 |
| `started_at` | 开始时间 |
| `finished_at` | 结束时间 |

## 6. Codex SDK 接入设计

系统以官方 Python SDK 路线为准：

```bash
pip install openai-codex
```

目标导入方式：

```python
from openai_codex import Codex, Sandbox
```

官方 SDK 会安装并使用匹配的 `openai-codex-cli-bin` runtime dependency，因此系统设计不依赖 WindowsApps 目录中的 Codex App 内置 `codex.exe`。

本系统不依赖用户全局 `~/.codex/config.toml`。项目级 Codex 配置使用独立 JSON 文件：

```text
config/codex.local.json
```

该文件保存本项目的 `api_key`、`base_url`、`model`、`model_provider` 等信息，并加入 `.gitignore`，不提交真实密钥。仓库只保留示例文件：

```text
config/codex.example.json
```

配置示例：

```json
{
  "api_key": "sk-your-api-key",
  "base_url": "https://api.openai.com/",
  "model": "gpt-5.4",
  "model_provider": "project-openai",
  "wire_api": "responses",
  "reasoning_effort": "high"
}
```

SDK 的 `CodexConfig` 不直接提供 `api_key`、`base_url`、`model` 字段。实现时需要：

1. 从 `config/codex.local.json` 读取项目配置。
2. 使用 `CodexConfig(config_overrides=...)` 向 Codex runtime 传入 CLI 配置项。
3. 使用 `codex.login_api_key(api_key)` 写入当前项目运行环境的认证信息。

推荐调用形态：

```python
from openai_codex import Codex, CodexConfig, Sandbox
from openai_codex import SkillInput, TextInput

config = load_project_codex_config()

codex_config = CodexConfig(
    config_overrides=(
        f'model_provider="{config["model_provider"]}"',
        f'model="{config["model"]}"',
        f'model_reasoning_effort="{config["reasoning_effort"]}"',
        f'model_providers.{config["model_provider"]}.name="{config["model_provider"]}"',
        f'model_providers.{config["model_provider"]}.wire_api="{config["wire_api"]}"',
        f'model_providers.{config["model_provider"]}.requires_openai_auth=true',
        f'model_providers.{config["model_provider"]}.base_url="{config["base_url"]}"',
    )
)

with Codex(codex_config) as codex:
    codex.login_api_key(config["api_key"])
    thread = codex.thread_start(
        cwd=project_dir,
        sandbox=Sandbox.full_access,
    )
    result = thread.run([
        SkillInput(
            name="academic-search-only",
            path=str((BASE_DIR / "skills" / "academic-search-only" / "SKILL.md").resolve()),
        ),
        TextInput(task_prompt),
    ])
```

后端封装 `CodexTaskRunner`，业务模块不直接调用 SDK。

| 配置项 | 建议值 | 用途 |
| --- | --- | --- |
| `cwd` | 当前项目目录 | 限定 Codex 工作范围 |
| `sandbox` | `Sandbox.full_access` | 不启用沙箱，允许联网检索、调用 API、下载开放 PDF 和写入本地文件 |
| `model` | 系统默认模型，可配置 | 便于后续调整 |
| `effort` | 按任务设置 | 研读、综述任务可用较高推理强度 |
| `config_overrides` | 从 `codex.local.json` 生成 | 覆盖模型、provider、base_url 等 |

任务调用原则：

- 保留 Codex agent runtime 的完整代理能力，不额外强行覆盖 `base_instructions`、`developer_instructions` 或 JSON 输出约束。
- 通过 `SkillInput` 显式传入当前任务需要的 skill，通过 `TextInput` 传入任务目标、输入文件和输出路径。
- 任务提示词必须明确使用指定 skill、以当前项目目录为工作范围、输出写入指定 Markdown / JSON 文件、完成后返回状态摘要。
- 系统不通过 Codex 沙箱限制能力；工作范围主要由 Web 后端的任务封装、`cwd`、项目目录结构、任务日志和结果文件审计共同保证。
- 文献检索任务需要联网访问 arXiv、Semantic Scholar、OpenAlex、Crossref、Unpaywall 等平台；实测 `Sandbox.workspace_write` 下可能出现 `network_access=false`，因此正式接入采用 `Sandbox.full_access`。

中文与编码验证：

- 已验证 Codex SDK 在 UTF-8 输入链路正常时可以理解中文任务，并能按中文要求输出结果。
- 曾出现“我没看懂你的请求”一类兜底话术，根因不是 Codex agent runtime 默认指令冲突，而是测试脚本经过 PowerShell here-string 传入 Python 时发生中文编码污染。
- 使用 Unicode escape 构造同一句中文后，SDK 记录中的 user message 为 `只回答两个字：正常`，最终输出为 `正常`。
- Web 后端实现时必须保证表单、JSON 请求体、临时任务文件、日志文件均使用 UTF-8 读写；不要让命令行编码成为正式调用链路的一部分。

典型任务流：

```text
论文研读任务：
输入：paper_id、PDF 路径、输出路径
工作目录：当前项目目录
允许写入：papers/<paper_id>/reading.json、library_papers.json、reading_notes.json
产出：文献矩阵结构化 JSON、研读状态回写、任务状态摘要
```

实现要求：

- 启动时检查 `openai_codex` 是否可导入。
- 检查 `config/codex.local.json` 是否存在且字段完整。
- 检查 API Key、base URL、模型名称、runtime 是否可用。
- 已验证 SDK 能使用项目级配置启动、完成 API Key 登录，并通过 `SkillInput` 接收项目内 `academic-search-only` skill。
- 正式任务不能只依赖提示词约束行为，应在 Web 后端记录任务输入、目标项目、输出文件、开始/结束时间和执行状态，便于追踪与回滚。
- SDK 仍处于 beta 阶段，API 变化由 `CodexTaskRunner` 内部适配。
- Web 页面只展示任务状态，不暴露底层 CLI / SDK 细节。
- 不依赖 WindowsApps 中的 Codex App 内置 `codex.exe`。

## 7. 系统实现路线

1. 项目创建：生成 `YYYYMMDD-HHMMSS-项目名` 目录，初始化 JSON 文件和基础目录。
2. 文献检索：Codex 先写入 `search_runs/*.json`，后端 normalizer 再统一合并更新 `candidate_papers.json`。
3. 导入知识库：从候选池导入到 `library_papers.json`，创建 `papers/<paper_id>/`。
4. PDF 管理：基于 `pdf_url` 下载开放 PDF 到 `papers/<paper_id>/paper.pdf`，并回写状态。
5. 论文详情与研读：读取 `library_papers.json`、`reading_matrix_fields.json` 和 `papers/<paper_id>/reading.json`，展示 PDF、文献信息、文献矩阵和论文问答。
6. 综述写作：自动刷新 `outputs/writing/writing_sources.csv`，通过四阶段工作台维护 `outline.md`、章节-文献映射、`survey.md` 和跨阶段 Codex 对话。
7. 导出：生成 `.xlsx` 和 `.bib`，用于课程报告、论文写作或外部工具。
